# 乐醒 v3：随机时间与AI详细功能规格

2026-10-27。继续功能与界面设计，暂不写应用代码。本文件定义目标体验；“现有”与“新增”分开说明，任何演示状态都不表示实际数据已写入。

## 本轮定位与范围

保留v2的提醒、音乐、日历、响铃、设置、历史和数据工具方案。本轮扩展两个重点：

1. 时间窗随机提醒：在允许的范围内随机开始响一次，与随机音乐独立组合。
2. 第三方Key驱动的任务型AI：连接服务后，围绕提醒和软件中的真实操作生成可核对草稿、建议与解释。

不为使用这两个功能额外创建乐醒云账户或强制购买乐醒会员。第三方模型服务的账户、权限和调用费用以服务商为准。未连接AI时，固定和随机时间提醒仍可在本地使用。

## 能力现状与设计增量

| 范围 | 当前项目可确认的基础 | 本轮新增设计 |
| --- | --- | --- |
| 提醒时间 | 固定事件时刻、多提前提醒点及重复规则 | 固定/随机时间模式、窗口所属日、抽取稳定性与错过状态 |
| 随机音乐 | 全局/专属池、一轮内尽量不重复 | 与随机时间的组合呈现、音源失效解释及修复建议 |
| AI连接 | 用户输入HTTPS地址、模型、Key；可选开启 | 服务商预设、少字段接入、连接检查和多连接档案 |

| AI应用 | 草稿校验、确认后新增 | 上下文选择、风险项逐项核对、变更记录与受保护撤销 |
| 解释 | 界面已有状态与历史 | 基于本地事实的排程原因、冲突和导入失败解释 |

当前数据结构没有时间窗随机模式；现有AI草稿也不能据此声称已支持该模式。本轮没有更改这些实现。

## 一、时间窗随机提醒

### 1. 用户看到的核心概念

同一“基本”分区中，时间方式分为“固定时刻”和“时间窗随机”。固定模式继续使用事件发生时间和多个提醒点。随机模式显示窗口开始、结束、是否跨日，以及“每个有效日期随机开始1次主提醒”。

随机模式中的窗口本身就是提醒安排，没有虚构的固定“事件发生时间”。因此“提醒点”分区在该模式下改名为“提醒方式”，配置强度、时长及可选额外动作。重复和音乐两个分区保留。

### 2. 默认行为

| 规则 | 目标行为 |
| --- | --- |
| 例子 | 08:00–08:10之间随机开始响铃一次 |
| 粒度 | 首版界面以整分钟选择；包含08:00和08:10，共11个候选时刻 |
| 分布 | 每个候选分钟机会相同，每个有效实例独立选择 |
| 连续同一时刻 | 允许偶然重复；不声称每天都会选不同分钟 |
| 生成次数 | 一份有效窗口实例只抽取一次并保留 |
| 主提醒次数 | 1次；重新打开应用或查看详情不增加次数 |
| 响铃时长 | 控制开始后的播放长度，可越过窗口结束；窗口约束的是开始时刻 |
| 稍后提醒 | 默认关闭；用户主动开启后，其手动稍后会产生额外提醒 |
| 固定补充提醒 | 默认关闭，开启需单独核对条件与时间 |
| 随机音乐 | 独立开关；不需要启用AI来每天选择时间或音乐 |
| 默认显示 | 展示窗口范围与“1次”，不把窗口开始假称为已抽中的时刻 |

5/10/15/30分钟作为长度快捷值，手动设置开始与结束时刻。窗口至少覆盖两个不同候选分钟，最长少于24小时。相同时刻提示改为固定提醒或扩大范围，不默认为24小时。

### 3. 创建、核对和显示

路径：新建提醒 → 基本 → 时间窗随机 → 起止时间 → 重复 → 提醒方式 → 音乐 → 核对保存。

核对页必须写清：所属日期、窗口、有效星期/日历策略、主提醒次数、稍后和固定补充是否启用、音乐范围，以及下一次有效窗口。

保存成功后，列表显示“08:00–08:10 · 随机1次”，而不是固定08:00。窗口开始前可显示“10分钟后进入时间窗”；窗口内显示“窗口进行中”。已经完成或错过的窗口不得继续伪装为待触发。

用户可以打开“查看本次已选时刻”，例如08:06。查看不会重新抽取。“只显示范围”只控制乐醒自己的界面，系统闹钟信息或通知可能显示准确时刻，不能承诺在整部手机上隐藏。

未来窗口可以只显示范围；为排程准备而产生的选择一经生效，必须在对应实例上保持稳定。首页倒计时展示的是已知状态：已显示具体时刻时才倒数到该分钟，未显示时只描述窗口。

### 4. 与重复、休班和结束日期结合

重复类型仍是单次、每日、每周、每月、每年、每N个日历日。每个匹配日期最多生成一个随机主提醒实例。先确定该日是否是有效重复日，再在该日窗口内选时间，不在每天重新抽决定是否应该提醒。

跨日窗口必须显式显示“次日”，例如周一23:55–次日00:10，窗口归属周一。星期、开始/结束日期与日历策略都按窗口开始日判定，避免午夜后被算成另一天又产生一次。

缺日策略沿用月/年规则，不因随机模式变得含糊。未知年度官方休班数据仍提示未收录，不让AI推测并自动认证。

### 5. 窗口已开始、已错过、重启与暂停

| 触发情景 | 必须采用的行为 |
| --- | --- |
| 开始前正常保存 | 在完整候选集合中选一次 |
| 首次创建时窗口已开始 | 默认从下一有效窗口开始；若用户明确选择今天，则展示剩余候选范围并从未来分钟中选一次 |
| 例：08:05:30首次创建 | 今天只剩08:06–08:10共5个候选分钟；核对页明确写范围已缩短 |
| 首次创建时窗口已结束 | 不立即补响；单次事件需改日期，重复事件展示下一有效窗口 |
| 已有实例的选定分钟已错过 | 记录错过；不偷偷在剩余窗口重抽并伪称原计划正常 |
| 应用重启、设备重启、更新 | 恢复同一实例与原选定时刻，不重新抽取；错过的实例仍按错过规则处理 |
| 暂停后恢复，原时刻仍在未来 | 继续原选定时刻 |
| 暂停后恢复，原时刻已过去 | 本次跳过，显示下一窗口；“今天再提醒”作为明确的新手动操作记录 |
| 首次保存、取消或重复点击 | 一份确认只能产生一份主提醒，取消不留下暗中生效的安排 |
| 系统能力不足 | 说明可能延迟；随机规则不能保证绕过权限或后台限制 |

“重新随机本次”仅在窗口尚未开始、尚未触发时提供，并要求明确点击与反馈；不自动重抽。改变起止范围是修改安排，展示新旧范围与作用范围，不能伪装成一次无影响的刷新。

### 6. 时间与时区边界

界面按当地时刻表达。时区变化后，尚未开始的窗口应保留选定的当地分钟并更新下一次实际安排，不因为重排不断换一个分钟。已经触发的实例保持已处理，不因时区或夏令时回拨重触发。

夏令时缺失的当地分钟不作为候选；重复出现的同一当地分钟只使用一次明确的发生时刻。整段窗口不存在时跳过并说明原因，不静默移到窗口外。这些是业务边界要求，本轮未确定具体实现方式或完成真机验证。

### 7. 一次主提醒与额外提醒

“严格一次”默认仅包含一次随机主提醒。强度与持续时间不增加触发次数。自动结束不会自动生成第二次主提醒。

用户可分别启用：

- **稍后**：响铃时由用户主动延后；明确提示可能超出窗口。
- **固定补充提醒**：例如08:10仍未明确确认起床时，再提醒。停止响铃不自动视为已经起床；采用什么确认条件在设置页说明。

启用任一选项后，摘要改为“1次随机主提醒＋可选额外提醒”。不得继续显示“总共只响1次”。固定补充与随机主提醒恰好同分钟时合并播放，保留两条来源；明确确认后取消该实例尚未发生的补充提醒。

该设计不强制算术题、拍照或扫描物品来关闭铃声。用户始终能明确结束当前声音。

### 8. 从多提醒点切换模式

固定事件已有提前10分钟、准时等多条提醒时，切到随机模式先展示影响：随机主提醒只保留1次，原多提醒点配置暂存，当前不会同时生效。用户可继续固定模式或确认切换；切回时可恢复原配置。

不静默删除原提醒点，也不将多个提前量全部套到随机选定时刻，造成窗口外或多次响铃。若用户想同时使用多个安排，应作为明确的额外安排独立添加和核对。

### 9. 冲突、编辑、日历与导入

不同事件同一分钟触发时沿用合并会话；仍分别记录各自窗口主提醒的完成情况。窗口与固定提醒相交表示“可能重合”，不能显示为已经确定冲突。

默认仍在完整窗口均匀选择，不暗中为避冲突改变分布。用户若选择错开，应明确修改范围或固定提醒，并重新核对。自动避让随机可用时段可作为后续独立模式评审，不混入首版。

编辑支持“仅本次 / 从下次起 / 整个重复规则”的目标体验，展示已发生实例不受影响；新例外安排与原规则在详情和历史中可以追溯。

日历同时提供窗口范围和实际已选时刻的查看方式。历史记录窗口、选定时刻、实际开始、延迟、音乐、停止结果和是否为额外提醒。

备份必须保留随机模式、范围、跨日、重复与额外提醒选择。旧版本无法表达这些规则时明确阻止或跳过相关条目，不把它悄悄改成固定时间。普通配置恢复不“重放”已结束窗口；实例历史与事件配置分开。

### 10. 效果观察

详见《时间窗随机提醒：证据与产品判断》。应用只记录自身可观测事实，用户自愿补填起床感受。结束响铃、触屏和实际清醒不能混用为同一个指标。AI可以描述记录，不输出未经验证的医学效果或自动改变窗口。

## 二、第三方Key的AI工作台

### 1. 入口与信息结构

设置中心保留“AI助手”。新建入口可选择“手动创建 / 用AI描述 / 从模板开始”；编辑器、事件详情、历史、导入预览可以提供轻量的上下文入口。底部仍是提醒、音乐、日历、设置四项，不增加AI专属底部页，不把首页变成聊天推广页。

AI工作台以任务为中心：创建提醒、修改所选、解释安排、分析汇总、整理文本、协助导入。进入后先显示当前上下文和任务范围，不默认上传完整事件库或完整历史。

### 2. 接入与“只填Key”的边界

已适配预设服务：选择服务商，填写Key，查看默认模型即可保存。自定义服务还需要正确的地址、协议和模型名；百炼等服务还可能要求选择与Key匹配的地域。因此，不能承诺任意第三方Key粘贴后都能跨服务直接使用。

| 连接类型 | 主页面字段 | 高级区域 |
| --- | --- | --- |
| DeepSeek预设 | 服务、Key、默认模型 | 服务地址、模型覆盖、兼容参数 |
| 百炼等已适配预设 | 服务、地域、Key、可用模型 | 地址与兼容选项 |
| 自定义兼容服务 | 连接名、HTTPS地址、模型、Key | 输出与超时等适配项 |

预设服务地址和默认模型应有更新日期，并允许用户核对。2026-10-27核对的DeepSeek官方文档列出兼容API和`deepseek-flash`等模型；百炼官方文档明确不同地域的端点、Key与模型列表不能混用。本轮界面中的预设据此示意，不保证长期不变。[DeepSeek官方文档](https://api-docs.deepseek.com/)、[百炼Key说明](https://help.aliyun.com/en/model-studio/get-api-key)

Key只在应用内输入，不要求用户在聊天里发给助手。默认遮盖，保存后显示“已保存”；替换和移除有明确入口。新服务不能读取旧服务的Key，不根据Key格式猜测并偷偷向多个服务尝试。

支持多个已保存连接档案，但每次请求只有一个明确的接收方。切换服务不会自动发送；失败不跨服务重试。第一阶段优先做少量可靠预设及自定义兼容入口，更多供应商逐个核对能力后再加入。

### 3. 连接检查

保存不联网。用户选择测试时，展示固定演示文本、目标地址和“可能产生少量服务商费用”，确认后执行。测试不附带提醒、音乐、历史或文件。

结果区分连接成功、Key无效、模型不存在、地域或套餐不匹配、余额/限流、超时和网络错误。成功只证明本次调用与被测试能力可用，不保证所有任务和未来请求都可用。

界面不展示含凭据的原始错误，不要求用户把Key复制到错误报告。网络关闭时显示“无法测试，配置已保留”。

### 4. 功能清单与深入场景

| 功能 | 用户可以怎样说 | 结果与边界 |
| --- | --- | --- |
| 自然语言创建 | “每周一到周五，8点到8点10随机提醒我起床，只响一次” | 生成窗口、星期、1次主提醒、额外提醒关闭的草稿；保存前核对 |
| 多提醒点创建 | “明天下午3点开会，提前半小时和准时提醒” | 固定事件＋两个提醒点，不误解为随机窗口 |
| 多事件整理 | 粘贴日程/课程文本 | 分条识别，保留来源片段，歧义项待补充，有效项可单独选择 |
| 上下文修改 | “把选中的提醒从下周起提前10分钟” | 先澄清改事件时间还是提醒提前量，展示作用范围和前后差异 |
| 批量改动 | “暂停下周这3项提醒，其他保留” | 只作用于显式选择集合，逐项核对，不能仅按同名猜测目标 |
| 规则解释 | “为什么周六没有这一项？” | 依据本地规则与日期计算给出原因；事实不足时说明未知 |
| 潜在重合 | “检查这周的提醒会不会撞在一起” | 本地先区分确定同刻与窗口可能重合，AI解释并给修改建议 |
| 生活安排拆解 | “给晨间流程安排提醒” | 用户先确认可用时间与最晚边界，生成草稿，不推断健康需求或保证效率 |
| 音乐池整理 | “把我选的这些曲目分成起床和休息两组” | 可依据用户标签和所选元信息提建议；不假装听过音频，不直接更改全局启用 |
| 历史/统计问答 | “最近是不是经常稍后？” | 使用选定区间匿名汇总，区分会话、提醒点、稍后与测试；不把停止当清醒 |
| 导入辅助 | “解释为什么这几项被跳过” | 读取用户选中的本地校验原因摘要，提供修正草稿，不自动上传整个备份 |
| 故障说明 | “为什么没有按选定时间响？” | 先展示本地计划/实际/权限事实，再可选用AI转述；未知原因不能编造 |

“提醒我喝水”“帮我早起”这类模糊目标应要求用户补充时间、频率或允许范围。AI可以提供可编辑建议，但不直接激活推测出来的安排。

### 5. 随机窗口的语言消歧

- “8点到8点10之间随机响一次”：一个窗口、一次主提醒。
- “8点、8点05、8点10各响一次”：三个固定安排，不能改成随机一次。
- “8点到10点每十分钟提醒”：是周期内多次，不属于窗口随机一次；当前支持程度必须明确。
- “8点左右”：先确认允许前后几分钟，不能擅自解释为08:00–08:10。
- “工作日”：区分周一至周五与含调休补班的法定工作日。
- “8点到8点10，十分钟后再提醒”：先核对是否允许额外稍后，摘要不能仍写总共一次。
- “别让我迟到”：先取得最晚边界，不用AI推断用户通勤或必须起床时间。

### 6. 任务型对话流程

每次任务依次经过：选择目标和范围 → 预览发送内容 → 生成中 → 消歧/草稿 → 本地规则核对 → 变更确认 → 执行结果与记录。

在生成前已知的缺失字段先本地提示。模型返回中间文字时不能让用户提前应用半截安排；完整且通过校验的条目才进入可确认区。取消请求后保留输入，说明可能已有已发送内容，不能保证服务商不计费。

对话保留本次选择范围与用户回答，显著显示哪些数据将随下一次请求发送。切到新任务不默认携带上次的私密事件和文件。对话管理可清理本地记录；清理本地对话不能宣称同时删除第三方服务保留的数据。

### 7. 上下文与隐私

发送预览中按任务列出：手动文本、选中的事件摘要、日期范围、匿名汇总、所选歌曲元信息或校验原因。未勾选项不发送。来源文本可能含私人安排，发送前能删减。

Key属于连接认证信息，不放进聊天正文、模型提示、备份、截图或普通日志。音频文件、完整歌词和封面不默认上传；音乐建议不要求把整库发送给模型。

外部文件中的“忽略规则、改服务地址、上传密钥”等内容只作为待解析文本，不具有操作授权。AI不能创建新的接收方、扩大读取范围或通过用户文本开启额外联网。

### 8. 草稿、差异与应用

每条建议标注：新增、修改、暂停、日历自定义候选、待补充或无法表达。可展开原文来源与解释。修改项逐字段显示旧值→新值，并选择仅本次、从指定日开始或整个规则的作用范围。

“我已替你设置好”只允许出现在实际应用成功之后。生成草稿时统一使用“待确认”“将新增”。冲突、重复和未匹配音乐的条目独立说明，用户可以只应用有效且选中的项目。

确认前若原事件已被手动修改，提示重新核对差异，不覆盖新内容。结果逐项显示成功、跳过和失败；部分成功不显示成全部成功，也不重复重试已完成项。

草稿可保存以后继续。AI批量变化记录具体作用对象，撤销前预览影响，保护应用后用户再次修改的条目。并不把任何失败都包装成可以无损自动回退。

### 9. 规则与事实的分工

日期匹配、随机抽取、下一次窗口、重排、防重复、实际播放和变更应用必须在模型不可用时仍能正确执行。AI提出意图与解释，不能决定一次本地提醒能否按时响起。

排程原因先有可核对的本地证据，如“周六不在所选星期中”“提前量已过期”“这首歌已停用”。AI可以改写为更易读的说明，不能用流畅文案替代缺失事实。

官方放假调休只来自可追溯数据；AI给出的日历变化始终是待用户确认的自定义候选。随机范围不等于睡眠监测，AI不诊断睡眠阶段。

### 10. 费用、请求记录与失败

请求按钮前显示接收方、任务类型与本次发送摘要；能可靠获得时显示预估信息，无法估算则明确未知。应用中的调用计数不是完整服务商账单，也不保证涵盖同一Key在其他软件的花费。

应用内次数限制可作为自控提示，但不能宣称是服务商侧的硬性费用封顶。限流、余额不足、模型不可用等错误由用户决定重试；不自动换更贵模型、不自动扩大输出、不跨主机发送。

服务切换、Key替换、模型变更保留为连接档案中的明确操作。失败时原输入、已选范围和草稿保留；允许转为手动创建。普通离线功能继续可用。

## 三、开发优先级建议

| 阶段 | 目标能力 | 完成条件 |
| --- | --- | --- |
| P0基础 | 提醒能力与运行状态准确、第三方连接预设、自然语言生成草稿、差异确认 | 不因AI网络问题影响本地提醒；不发生未确认写入或密钥外泄 |
| P1核心增量 | 时间窗随机一次、范围与重复边界、随机语义识别、上下文修改、批量核对 | 严格一次可理解；重启/恢复不重抽；固定模式保持原体验 |
| P1解释与恢复 | 排程原因、潜在重合、导入原因、变更记录与保护性撤销 | 有事实依据，作用范围和部分失败可追溯 |
| P2增强 | 音乐分组建议、使用观察与可选AI汇总、更多经过验证的服务商档案 | 不伪造音频分析或健康效果；更多调用有明确用户价值 |

此处是产品优先级，不是具体技术实现计划。模型调用、手机排程、数据结构与性能方案在设计评审后再确定。

## 四、必须通过的验收情景

| 情景 | 预期结果 |
| --- | --- |
| 08:00–08:10正常窗口 | 候选分钟包含端点；仅1次随机主提醒，默认无稍后和补充 |
| 连续两天同一分钟 | 允许且解释为随机可能重复，不能偷偷改成保证不重复 |
| 多次打开、重启或更新 | 已选实例时刻不变，不多生成主提醒 |
| 首次创建时08:05:30 | 明确今天范围缩短至08:06–08:10，用户选择后才使用 |
| 已有实例08:03被错过 | 不自动重抽08:06冒充正常执行 |
| 跨午夜窗口 | 归属开始日，星期和结束日期不误判为两次 |
| 回拨、时区、缺失分钟 | 已处理实例不重复，无法出现的时刻说明处理结果 |
| 固定多点切到随机 | 展示影响，原配置暂存，确认后仅一条主提醒生效 |
| 开启额外提醒 | 摘要明确可能多次；与严格一次区分 |
| 结束声音 | 不自动报告已经起床或清醒 |
| 未启用AI、离线 | 时间窗与音乐仍按保存规则运行 |
| 任意Key粘贴 | 只向用户选定服务测试；不猜测或遍历其他接收方 |
| 模型或地域不匹配 | 配置和输入保留，给明确修正入口 |
| “8点左右”“工作日” | 先消歧，未确认不激活推测规则 |
| AI生成窗口并建议稍后 | 提醒用户这将增加次数，不能仍写总共一次 |
| AI上下文编辑 | 明确修改的是事件时刻、窗口还是提前量；展示范围和差异 |
| 待确认期间事件已改变 | 重新核对，不覆盖用户的新修改 |
| 文件里夹带操作指令 | 不改变接收方、权限和发送范围 |
| AI分析停止记录 | 只能报告停止行为，不换算唤醒成功率 |
| 部分应用成功 | 逐项结果，重试不重复创建已成功项 |

本轮提供这些情景的规格、界面示例和本地文件验证。尚未运行真实排程、调用任何第三方API或进行唤醒效果测试。
